FEATURE 01

ガチャ演出の割合設定

参考モデル: 他社事例A（管理コンソール） ／ 当初要望: 2026-08-01 18:21

見積工数 4 人日

参考画面

他社事例A: 賞ごとに「S賞の演出割合設定」モーダルが開き、演出セレクト＋%入力の行が5つ固定で並ぶ。

賞のヘッダ部に現在の割合サマリ（標準S:100%）と［編集］ボタンが常に見えている。

仕様

目的1つの賞に複数の当たり演出を登録し、出現割合を%で配分できるようにする。景品1件ごとに演出を指定する既存機能はそのまま残す。
適用範囲S / A / B / C / D ＋ その他のすべての賞ランク。賞ごとに独立した設定を持つ。
スロット数他社事例Aの5行固定に対し10行以上に拡張。実装は可変行（［+ 演出を追加］で行を増やす）とし、上限は設定なし（無制限）を第一希望、性能・UI上の制約がある場合は実現可能な最大値を提示いただきたい。
割合の扱い合計100%を必須とする。100%未満／超過は保存不可（エラー表示）。［残りを自動配分］で未入力行に均等割り当て。小数第1位まで許容するか要判断（推奨: 整数のみ）。
抽選方法当選判定後、その賞に登録された演出から設定割合に従って1つを選択して再生。抽選結果そのものには影響しない（演出の見た目のみ）。
景品個別演出との優先景品明細に個別演出が設定されている場合は個別演出を優先。未設定の景品にのみ賞の割合設定を適用（要合意）。
表示賞ヘッダに現在の配分サマリ（例:「モノ虹 60% / 金 30% / 銀 10%」）を表示。長い場合は先頭2件＋「他◯件」。
実装時の確認ポイント
  • 可変行の上限: 無制限が可能か。難しい場合の推奨上限と、その理由（保存データ構造・抽選処理）
  • 既存データの移行: 現行の単一演出設定を「その演出100%」として自動移行できるか
  • 景品個別演出との優先ルール実装コスト

モック（操作できます）

tora console / oripa / edit — 演出割合設定MOCK

S賞の演出割合設定

行は自由に追加・削除できます。合計が100%になると保存できます。

合計 0%

FEATURE 02

管理画面のメニュー単位ロック

新規設計（弊社設計案） ／ 起点: 2026-08-01 18:24「管理サイトの権限」→ 8/27 パスコード方式で整理

見積工数 3 人日

設計方針

ロール管理（項目ごとの権限マスタ）はユーザー・役割・画面のマトリクス設計が必要で工数が大きくなるため、まずは「見せたくないメニューにパスコードの鍵をかける」方式で先行実装する案です。運用は「事務所内の共有PCで、配信者や外部の人に画面を見られたくない」ケースを想定しています。

仕様

ロック単位サイドメニューの項目単位（例: 決済ログ・ユーザー・課金アイテム・配送 など）。管理画面の設定ページで、メニュー一覧に対しトグルでロックのON/OFFを切り替える。
解除方法ロック中のメニューをクリックするとパスコード入力モーダルが開く。数字4〜6桁。正しければそのメニューが開く。
パスコード管理既定はサイト共通のコード1本。必要に応じメニュー個別のコードも設定可（未設定なら共通コードを使用）。コードはハッシュ化して保存し、平文では表示しない（再設定のみ可）。
解除の有効時間解除後はそのブラウザで15分間（値は設定可）再入力なしで閲覧可能。タブを閉じる／ログアウトで即破棄。「常時解除」は用意しない。
保護の範囲メニューを隠すだけでなくサーバー側でも該当ページ・APIを検証する。URL直打ち・APIの直接呼び出しでも解除前は403とする（画面上の非表示だけでは保護にならないため）。
失敗時の扱い連続5回失敗で10分間ロックアウト。解除の成功・失敗を操作ログに記録（日時・アカウント・対象メニュー）。
例外設定特定アカウント（オーナー等）をロック免除にする設定を持つ。パスコードを忘れた場合はオーナーアカウントから再設定。
将来拡張この仕組みを土台に、後からロール別権限（閲覧のみ／編集可）へ拡張できるデータ設計とする。
実装時の確認ポイント
  • サーバー側検証を含めた場合の工数（画面側だけの実装との差分）
  • 解除状態の保持方法（セッション／短期トークン）と有効時間設定の実装コスト
  • 操作ログ・ロックアウトを含めるかどうかで工数がどれだけ変わるか

FEATURE 03

キリ番の同一景品まとめ表示

参考モデル: 他社事例B（管理コンソール） ／ 当初要望: 2026-08-10 23:06

見積工数 — 弊社対応分のため費用は発生しません

参考画面

他社事例B: カードごとに1つの親行を持ち、その下に「通常」「キリ番」の明細行がぶら下がる構造。親行に合計個数（通常◯/キリ番◯）と表示形式（まとめて表示）のセレクトがある。

明細行では状態・交換コイン・配送限定・当たり演出を個別に設定でき、［キリ番追加］で既存行の値を初期値とした入力行が開く。

仕様

課題現状はキリ番を設定すると同一カードでも別々の景品として並んでしまうため、ラインナップ一覧が冗長になる。
データ構造カード＝親、通常／キリ番＝明細の親子構造にする。親行はカード情報と合計個数（内訳: 通常◯ / キリ番◯）を持つ。
明細の項目種別（通常／キリ番）・状態・交換コイン・配送限定・当たり演出・個数／キリ番。明細ごとに個別適用。
キリ番の入力複数キリ番をカンマ／スペース区切りで一括入力（例: 1, 100, 1000）。［キリ番追加］は既存明細の状態・コイン・配送・演出を初期値として引き継ぐ。
表示形式親行のセレクトで「まとめて表示」／「個別に表示」を選択。まとめて表示ではフロントのラインナップに1枚のカードとして出し、個数は合計を表示。
まとめ判定同一カードでも状態（美品/普通等）または配送限定が異なる明細は別カードとしてフロント表示する（他社事例Bの注意書きと同仕様）。
既存データ移行現在バラバラに登録されているキリ番景品を、同一カードIDで自動的に親子へ寄せる移行処理が必要。
実装時の確認ポイント
  • 既存ガチャのデータ移行（現行のフラットな景品行 → 親子構造）の可否と工数
  • 抽選ロジック側への影響（明細単位で口数を持つ形になるため、シャッフル生成に変更が入るか）
  • フロント側のラインナップ表示・獲得景品表示の改修範囲
