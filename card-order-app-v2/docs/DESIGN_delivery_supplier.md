# 納品基準・問屋連携システム 設計書

対象アプリ: card-order-app-v2（トレカ商事 受発注・請求システム）
背景: 経営管理部との合意により、**物流を伴う取引（カード卸・什器備品等）を「納品完了日」で収益認識**する。問屋の入荷→出荷→納品をシステム化し、自動出荷通知・納品報告書の発行基点・多問屋（A/B/C…）拡張の基盤を構築する。
※ 物流を伴わない取引（運用手数料 GMV×2.4% 等）は従来どおり（発生／請求基準）。

## 確定した方針（2026-07-10）
- **収益認識点＝納品完了**: 問屋が「納品完了」を登録した日（`delivered_at`）を収益認識日とする。**ショップの受領確認を任意で証跡**として保持（実務性と監査性の両立）。
- **入荷登録**: 問屋が新商品を下書き登録 → **管理者が承認して公開**（価格・掛け率の統制）。
- **進め方**: 段階リリース（フェーズ1から即実装）。

## ロール
既存 `shop / admin / super_admin` に **`supplier`（問屋）** を追加。
- 問屋ユーザーは1つの問屋に所属（`supplier_users`, 1ユーザー=1問屋）。
- 問屋は自社商品・自社関連の出荷/納品のみ閲覧・更新（RLSで分離）。

## データモデル
- **suppliers**（問屋マスタ）: 問屋A/B/C… `name, code, contact, email, phone, address, active`
- **supplier_users**: 問屋ユーザー↔問屋（`supplier_id, user_id`）
- **products.supplier_id**: どの問屋の商品か
- **shipments**（出荷・納品／フェーズ2）: `supplier_id, shop_id, status(準備中/出荷済/配送中/納品完了), shipped_at, carrier, tracking_number, delivered_at, delivery_report_no`
- **shipment_items**（フェーズ2）: 出荷↔発注明細（複数発注まとめ出荷・分割/部分納品に対応）
- **収益認識**: `delivered_at` を会計レポート/エクスポートの基準日に。ショップ受領は `received_at` として証跡。

## フロー
```
入荷登録(問屋) → 承認公開(管理者) → ショップ発注 → 管理者確定
  → 問屋が出荷情報入力(出荷済) → 【自動】ショップへ出荷通知
  → 配送中 → 問屋が納品完了(delivered_at) → 【収益認識点】
      + ショップ受領確認(任意・証跡) + 納品報告書PDF発行 + 会計反映
```

## 問屋専用画面 `/supplier`（平易・ガイド付き）
- ダッシュボード: 要出荷オーダー一覧（自社商品の確定発注）
- 入荷登録: 新商品（JAN/価格/カートン/発売日/数量）を下書き→承認待ち
- 出荷更新: 確定発注を選び出荷日・配送会社・追跡番号→納品完了まで
- 納品報告書の確認

## 実装フェーズ
1. **基盤**: suppliers＋supplier_users＋supplierロール＋認証/RLS＋管理の問屋管理＋問屋ダッシュボード ← 本フェーズ
2. 出荷更新画面（shipments）＋自動出荷通知（現行メール運用を置換）
3. 納品完了＋`delivered_at`＋収益認識日＋納品報告書PDF＋会計レポート納品基準化
4. 入荷登録（問屋下書き→管理者承認公開）
5. 多問屋オンボーディング整備

## 拡張性
問屋の追加＝`suppliers` に行追加＋問屋ユーザー招待のみ。画面・ロジックは `supplier_id` で汎用化しているため A/B/C… と増えても改修不要。
