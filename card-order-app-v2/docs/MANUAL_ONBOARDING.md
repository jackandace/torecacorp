# 新人スタッフ研修マニュアル — トレカ商事カンパニー 卸事業

トレカ商事カンパニー（PALETTE GROUP）の卸事業と受発注システムの全体像を、
新しく参加するスタッフ向けにまとめたものです。操作手順の詳細は
[管理者向け操作マニュアル](MANUAL_ADMIN.md) を参照してください。
ここでは「**なぜそうなっているか**」と「**何をやると事故るか**」に重点を置きます。

---

## 1. このビジネスとアプリが解決していること

トレカ商事カンパニーは、**問屋から仕入れたトレーディングカード商品を、
全国のカードショップへ卸す**事業です。以前はメール・Excel・電話で
受発注〜請求を回していましたが、次の問題がありました。

- ショップごとの発注希望の集計・配分が手作業で、ミスと漏れが起きる
- 掛け率・リベート（ランク割引）の計算が属人化
- 請求書発行・入金消込・保証金精算の追跡が困難
- 「誰がいつ何を変更したか」が残らない

受発注システム（卸アプリ）はこれらを一元化し、**発注受付 → 配分 → 出荷 →
請求 → 入金 → リベート反映**までを1つの流れで管理します。

## 2. 登場人物と役割

| 立場 | 誰 | 役割 |
|---|---|---|
| 問屋（仕入元） | 橋本さん | 入荷案内リスト（Excel）の提供、発注の受付、商品の出荷。**発注締切の起点** |
| 自社（卸元） | 鈴木さん・河津さん ほか | 商品公開、発注の配分・確定、請求・入金消込、ショップ対応 |
| ショップ（顧客） | 全国のカードショップ約100店 | アプリから発注。**実店舗を持つ事業者のみ**（ECのみは取引不可・審査制） |
| システム | 卸アプリ | 上記全員をつなぐ。ショップ画面と管理画面に分かれる |

お金の流れ: **ショップ → 自社 → 問屋**。商品の流れ: **問屋 → (自社経由または直送) → ショップ**。
自社の粗利は「案内掛け率と実掛け率の差」から生まれ、そこからリベートを還元します。

## 3. 取引の全体フロー

```
問屋: 入荷案内リスト(Excel)
  ↓ ① 在庫管理へ取込・設定確認・公開
ショップ: アプリで発注リクエスト
  ↓ ② 締切まで希望を受付 (締切 = 問屋締切の3日前)
自社: 配分・数量確定 → 問屋へ発注
  ↓ ③ 確定するとシステム在庫が減る
問屋: 出荷 (追跡番号)
  ↓ ④ 納品完了 = 売上計上のタイミング
自社: 請求書発行 → ショップ入金 → 消込
  ↓ ⑤ 月次でランク・リベート更新
```

## 4. 商品の2つのフロー — 「配分品」と「カット割」

商品には2種類あり、**扱いが全く違います**。取り違えると金額事故になります。

### 配分品（haibun）
在庫数が決まっている商品。ショップの希望を集めて在庫の範囲で配分します。

- ステータス: リクエスト → 仮確定 → 確定
- 在庫上限あり。**ショップごとに発注可能数までしか希望を出せない**
  （複数ショップの希望合計が在庫を超えるのは正常。誰にいくつ配るかは自社が決める）
- 請求は確定後にまとめて発行（通常請求）

### カット割（cut）
メーカー都合で入荷数が変動する商品。希望数で受け付け、後で数量が「カット」されます。

- ステータス: リクエスト → 発注調整中 → 仮確定 → 確定
- 在庫上限なし（希望BOX数をそのまま受付）
- **保証金（前受金）を先に請求** → 数量確定後に最終精算（→ 6章）

## 5. リベート・ランク制度

ショップの**月間発注額**（仮確定+確定ベース）に応じてランクが決まり、
リベート率分が請求時に自動で値引きされます。

| ランク | 月間発注額 | リベート率 |
|---|---|---|
| プラチナ | 100万円以上 | 10% |
| ゴールド | 50万円以上 | 7% |
| シルバー | 20万円以上 | 5% |
| ブロンズ | 10万円以上 | 3% |
| スタンダード | — | 0% |

- 昇格は**翌月1日に自動反映**。降格は「昇格基準の50%未満が続くと1ヶ月猶予後に1ランク」
- 累計取引額による最低ランク保証あり（長期取引の優良店が単月不振で落ちすぎない仕組み）
- **掛け率**: ショップに見せる「案内掛け率」= 問屋の実掛け率 + 上乗せ率。
  ショップ個別の掛け率設定（rate_override）があればそちらが優先

### 請求金額の計算式（暗記推奨）

```
小計(税抜)   = 定価 × 確定BOX数 × 案内掛け率   …切り捨て
リベート     = 小計 × リベート率              …切り捨て
手数料(税抜) = 小計 × 2%                      …四捨五入 (決済手数料)
課税対象額   = 小計 − リベート + 手数料
消費税       = 課税対象額 × 10%               …切り捨て
請求合計     = 課税対象額 + 消費税
```

⚠ **リベート率の変更（ランク設定変更）は即時反映されず翌月1日適用**。
当月の集計・請求を壊さないための仕様です。「変えたのに反映されない」は正常。

## 6. 保証金（前受金）の仕組み — カット割専用

カット割は入荷数が読めないため、発注時に**保証金**を先に請求します。

```
保証金 = 定価 × 希望BOX数 × 案内掛け率 × 保証金率
```

- **保証金率は既定30%**（商品ごとに設定可・発行時に30/40/50%から選択可）
- **前受金なので消費税・リベートは掛かりません**（請求書は「非課税」表記）
- 数量確定後に「最終精算」: 確定数量の満額（リベート・手数料・税込）から
  預かった保証金を差し引き、**差額請求（精算）** または **返金（支払通知書）** を発行
- 請求書のバッジ: `保証金` → `精算` or `返金` で親子関係が追える

**精算の例**（定価2,970円 / 掛け率88% / 50BOX希望 → 40BOX確定 / 保証金30%）:
保証金 ¥39,195 を先に入金 → 確定満額(税込・手数料込) ¥117,271 → 差額 ¥78,076 を請求。

⚠ 保証金の入金を確認する前に問屋へ発注しない（入金なしキャンセル時は保証金没収の規約）。

## 7. 請求・入金・出荷までの流れ

### 請求・入金
1. 確定済み発注から請求書を発行（自動計算・プレビューあり）
2. ショップが振込 → **ショップは「振込完了を報告」できる** → 請求一覧に
   「🔔 支払い確認中」表示 + 社内へ通知メール
3. 通帳/明細で入金確認 → 請求詳細で「入金を記録」（消込）→ 入金済み
4. 入金済みになると領収書PDFを発行可能

⚠ **消込は必ず実際の入金を確認してから**。ショップの「振込報告」は自己申告であり、
消込の代わりにはなりません。

### 出荷
確定 → 出荷準備 → 出荷済（追跡番号入力で自動通知）→ 配送中 → 完了。
**納品完了日（delivered_at）が売上計上（収益認識）の基準日**です。
カートン単位配送の商品（📦マーク）は端数出荷ができない点に注意。

## 8. ⚠ 事故ポイント集 — 実際に起きたトラブルから

すべて実際に発生した事例です。同じ轍を踏まないでください。

### 事故1: Excel取込後の「カートン数・最低発注数」放置
入荷案内リストには**カートン数の列が無い**ため、取込した商品は
カートン数・最低発注数とも**既定の12**で登録されます。
実際は24入りの商品や、12BOX未満の少数配分の商品もあります。

- **カートン24の商品が「1CT=12BOX」のまま公開** → ショップが誤発注
- **8BOX配分なのに最低発注数12** → 誰も発注できない（公開前チェックに警告が出ます）

→ **取込のたびに、カートン数と最低発注数を商品編集で確認・修正する。**
取込結果画面の黄色い注意書きと、公開前チェックの警告を必ず読む。

### 事故2: 発注が「リクエスト止まり」のまま締切超過
在庫の引き当てはステータス**「確定」時のみ**。リクエストのまま放置すると
在庫も動かず問屋発注も漏れます。発注一覧の「要確定」表示と締切バナーを毎日確認。

### 事故3: 招待メール・パスワード設定リンクの罠
- 設定リンクは**1時間有効**。法人メールのセキュリティが原因の無効化は
  対策済み（ページを開いただけでは消費されない方式）だが、**「届いてから
  1時間以内に設定ボタンまで完了」**とショップに案内すること
- 再送すると**古いリンクは失効**する。必ず最新のメールを使ってもらう
- 再送ボタンは登録済みユーザーへは自動でパスワード設定メールに切り替わる（画面表示で確認できる）

### 事故4: 保証金請求書に消費税を載せる/税込表記する
保証金は前受金＝**非課税**。システムは自動で非課税計算・表記するが、
手動で金額をいじったり、Excelで別途請求書を作るときに混ぜないこと。

### 事故5: ランク・リベートを「今月から」変えたつもりになる
設定変更は**翌月1日適用の予約**。顧客に「今月から○%にします」と
約束しないこと。個別対応が必要なら掛け率の個別設定（rate_override）を使う。

### 事故6: テスト・手入力データの放置
テストで作った発注・請求は集計（売掛・KPI・ランク計算）に乗ります。
テストデータは必ず削除またはアーカイブ（deleted_at）し、
本番での動作確認は専用のテストショップ（鈴木テスト商店）で行う。

### 事故7: なりすまし系の変更をチャットで受ける
**配送先住所・返金先口座の変更は申請制**（アプリ内申請 → 自社確認 → 承認）。
メールや電話で「配送先変えて」と言われてもその場で変えない。
会社名・登録住所・メールの変更は本人確認のうえ管理者のみが行う。

## 9. 困ったときの調べ方

| 知りたいこと | 見る場所 |
|---|---|
| 操作手順の詳細 | 管理画面の「操作マニュアル」/ [MANUAL_ADMIN.md](MANUAL_ADMIN.md) |
| 誰がいつ何を変更したか | 管理画面「監査ログ」（super_admin） |
| 仕様がいつ・なぜ変わったか | [CHANGELOG.md](CHANGELOG.md)（重要変更の日時付き記録） |
| メールが届いたか | Resend ダッシュボード / 通知センターの送信履歴 |
| バッチが動いたか | リベート管理の変更ログ / batch_logs |
| 在庫数が合わない | 発注詳細の操作履歴 + 監査ログで増減を追跡 |

わからないことは推測で操作せず、鈴木さん・河津さんに確認してください。
**金額・在庫・顧客情報に触る操作は、迷ったら止まる**が鉄則です。
