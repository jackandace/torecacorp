# 新人スタッフ研修マニュアル — トレカ商事カンパニー 卸事業

トレカ商事カンパニー（PALETTE GROUP）の卸事業と受発注システムの全体像を、
新しく参加するスタッフ向けにまとめたものです。操作手順の詳細は
[管理者向け操作マニュアル](MANUAL_ADMIN.md) を参照してください。
ここでは「**業界の構造と慣わし**」「**なぜそうなっているか**」
「**何をやると事故るか**」に重点を置きます。

---

## 1. このビジネスとアプリが解決していること

トレカ商事カンパニーは、**問屋から仕入れたトレーディングカード商品を、
全国のカードショップへ卸す**事業です。以前はメール・Excel・電話で
受発注〜請求を回していましたが、集計・配分の手作業ミス、掛け率・リベート
計算の属人化、請求・入金・保証金精算の追跡困難、変更履歴が残らない、
といった問題がありました。

受発注システム（卸アプリ）はこれらを一元化し、**発注受付 → 配分 → 出荷 →
請求 → 入金 → リベート反映**までを1つの流れで管理します。

## 2. 業界の流通構造と自社のポジション

トレカの流通は多段階の問屋構造です。自社がどこにいるかをまず把握してください。

```
メーカー (株式会社ポケモン / バンダイ など)
  ↓
1次問屋 (メーカーと直接口座を持つ大手)
  ↓
2次問屋 (橋本さん) ← 自社はここの商品の「販売先」を集めている
  ↓
トレカ商事カンパニー (自社)
  ↓
カードショップ (全国 約100店)
```

- 自社は**2次問屋（橋本さん）の販売網**として、全国のショップから発注を
  集約する立場。上流(メーカー・1次)と直接の取引口座はない
- 商品・数量・掛け率は橋本さんの「入荷案内リスト」で降りてくる。
  **上流で数量が決まるため、自社の意思で仕入数を増やせない**——これが
  後述する「ティア1不足」問題の根本です

### 収益構造（粗利の作り方）

```
ショップへの案内掛け率 = 問屋（橋本さん）の実掛け率 + 上乗せ 3〜5%
                          （タイトルごとに実掛け率が違うため上乗せ幅も変わる）
＋ 取引手数料 税抜2%（税込2.2%相当・全請求に計上）
─────────────────────────────
→ 平均粗利 5〜7% 程度
```

薄利のため、**数量ミス・配分ミス・請求ミスがそのまま利益を消します**。
1件の誤請求の損失を取り返すには何十件分の取引が必要、という感覚を持ってください。

## 3. 登場人物と役割

| 立場 | 誰 | 役割 |
|---|---|---|
| メーカー・1次問屋 | （直接取引なし） | 供給量・規制ルールの決定元。販売店調査やフライング販売規制はここ発 |
| 2次問屋（仕入元） | 橋本さん | 入荷案内リスト（Excel）の提供、発注受付、商品の出荷。**発注締切の起点** |
| 自社（卸元） | 鈴木さん・河津さん ほか | 商品公開、発注の配分・確定、請求・入金消込、ショップ対応 |
| ショップ（顧客） | 全国のカードショップ約100店 | アプリから発注。**実店舗を持つ事業者のみ**（審査制・→9章） |
| システム | 卸アプリ | 上記全員をつなぐ。ショップ画面と管理画面に分かれる |

お金の流れ: **ショップ → 自社 → 問屋**。商品の流れ: **問屋 → ショップ**。

## 4. タイトルのティア構造 — 現状の最重要課題

扱うタイトルには事実上の「ティア（格）」があり、**ビジネスの力学はほぼ
これで決まります**。新規対応・配分判断の前提知識として必ず理解してください。

| ティア | タイトル例 | 現状 |
|---|---|---|
| ティア1 | ポケモンカード、ワンピース、ユニオンアリーナ | **数がほとんど取れない**。需要は圧倒的 |
| ティア2 | 遊戯王、デュエル・マスターズ、ヴァイスシュヴァルツ 等 | **売上の大半はここ**。供給は比較的安定 |
| ティア3以下 | その他マイナータイトル | 供給余力あり。買い手がつきにくい |

### この構造から生まれる力学

- 誰もが欲しいのはティア1。しかし供給が細いため、**数少ないティア1は
  取引実績の多いショップへ優先案内**せざるを得ない
- 新規ショップから見ると「ポケカ目当てで取引を始めたのに買えない」
  構図になりやすい。**ここが不満とクレームの最大の発生源**
- 自社として本当にありがたいのは**ティア2以下を継続的に仕入れてくれる
  ショップ**。実績を積んだショップにティア1が回る、という好循環を作りたい
- 根本解決は**問屋開拓（仕入ルートの複線化）でティア1の供給量を増やす**こと。
  それまでは「期待値の調整」が顧客対応の中心スキルになる

### 顧客対応での伝え方（重要）

- ティア1が「十分に買える」と期待させる説明をしない。
  「実績に応じて優先案内」「まずはティア2でお取引実績を」と一貫して伝える
- 配分は**受注後に最終決定**する方式のため、「仕入れられると思ったのに
  買えなかった」という不満が構造的に発生する。発注時点で確約と受け取られる
  表現（「取れます」「大丈夫です」）を使わない

## 5. 取引の全体フロー

```
問屋: 入荷案内リスト(Excel)
  ↓ ① 在庫管理へ取込・設定確認・公開
ショップ: アプリで発注リクエスト
  ↓ ② 締切まで希望を受付 (締切 = 問屋締切の3日前)
自社: 配分・数量確定 → 問屋へ発注
  ↓ ③ 確定するとシステム在庫が減る
問屋: 出荷 (発売日当日着・→10章)
  ↓ ④ 納品完了 = 売上計上のタイミング
自社: 請求書発行 → ショップ入金 → 消込
  ↓ ⑤ 月次でランク・リベート更新
```

## 6. 商品の2つのフロー — 「配分品」と「カット割」

商品には2種類あり、**扱いが全く違います**。取り違えると金額事故になります。

### 配分品（haibun）
在庫数が決まっている商品。ショップの希望を集めて在庫の範囲で配分します。

- ステータス: リクエスト → 仮確定 → 確定
- 在庫上限あり。**ショップごとに発注可能数までしか希望を出せない**
  （複数ショップの希望合計が在庫を超えるのは正常。誰にいくつ配るかは自社が決める）
- 請求は確定後にまとめて発行（通常請求）

### カット割（cut）
メーカー都合で入荷数が変動する商品。希望数で受け付け、後で数量が「カット」されます。

- ステータス: リクエスト → 発注調整中 → 仮確定 → 確定
- 在庫上限なし（希望BOX数をそのまま受付）
- **保証金（前受金）を先に請求** → 数量確定後に最終精算（→ 8章）

## 7. リベート・ランク制度

ショップの**月間発注額**（仮確定+確定ベース）に応じてランクが決まり、
リベート率分が請求時に自動で値引きされます。ティア2以下を継続的に
仕入れてくれるショップに還元し、実績を可視化する仕組みでもあります。

| ランク | 月間発注額 | リベート率 |
|---|---|---|
| プラチナ | 100万円以上 | 10% |
| ゴールド | 50万円以上 | 7% |
| シルバー | 20万円以上 | 5% |
| ブロンズ | 10万円以上 | 3% |
| スタンダード | — | 0% |

- 昇格は**翌月1日に自動反映**。降格は「昇格基準の50%未満が続くと1ヶ月猶予後に1ランク」
- 累計取引額による最低ランク保証あり（長期取引の優良店が単月不振で落ちすぎない）
- **掛け率**: 案内掛け率 = 実掛け率 + 上乗せ率（→2章）。
  ショップ個別の掛け率設定（rate_override）があればそちらが優先

### 請求金額の計算式（暗記推奨）

```
小計(税抜)   = 定価 × 確定BOX数 × 案内掛け率   …切り捨て
リベート     = 小計 × リベート率              …切り捨て
手数料(税抜) = 小計 × 2%                      …四捨五入 (取引手数料)
課税対象額   = 小計 − リベート + 手数料
消費税       = 課税対象額 × 10%               …切り捨て
請求合計     = 課税対象額 + 消費税
```

⚠ **リベート率の変更（ランク設定変更）は即時反映されず翌月1日適用**。
当月の集計・請求を壊さないための仕様です。「変えたのに反映されない」は正常。

## 8. 保証金（前受金）の仕組み — カット割専用

カット割は入荷数が読めないため、発注時に**保証金**を先に請求します。

```
保証金 = 定価 × 希望BOX数 × 案内掛け率 × 保証金率
```

- **保証金率は既定30%**（商品ごとに設定可・発行時に30/40/50%から選択可）
- **前受金なので消費税・リベートは掛かりません**（請求書は「非課税」表記）
- 数量確定後に「最終精算」: 確定数量の満額（リベート・手数料・税込）から
  預かった保証金を差し引き、**差額請求（精算）** または **返金（支払通知書）** を発行
- 請求書のバッジ: `保証金` → `精算` or `返金` で親子関係が追える

**精算の例**（定価2,970円 / 掛け率88% / 50BOX希望 → 40BOX確定 / 保証金30%）:
保証金 ¥39,195 を先に入金 → 確定満額(税込・手数料込) ¥117,271 → 差額 ¥78,076 を請求。

⚠ 保証金の入金を確認する前に問屋へ発注しない（入金なしキャンセル時は保証金没収の規約）。

## 9. 新規ショップ — 問い合わせから取引開始まで

新規問い合わせの大半は「**ポケカ・ワンピを仕入れたい**」です。しかし
4章の構造上、**多くは取引をお断りせざるを得ません**。入口の基準を
理解し、期待値を正しく設定することが最初の顧客対応です。

### 取引の最低条件（メーカー規制・信用の観点）

| 条件 | 理由 |
|---|---|
| **実店舗の運営**（ECのみは不可） | 販売店調査・転売対策の業界要件。登録フォームでもECのみは弾かれる |
| **運営歴 1〜2年以上** | 歴のない店舗は業界的に信用ゼロ。**ティア1はこの実績がないと取引のテーブルに載らない** |
| 利用注意事項・免責事項への同意 | 宣誓書・開業届等の提出を含む |

### 受け入れフロー

```
メール問い合わせ → 簡易ヒアリング（運営形態・実店舗の運営歴）
 → 条件確認 → 招待リンク発行 → ショップが登録・規約同意
 → 内容確認のうえ active 化 → 取引開始
```

### 新規対応で必ず伝えること

- 取引開始＝ティア1が買えることではない。**「取引できても十分に仕入れ
  られるとは限らない」**のが現状であること
- 実績（ティア2以下の継続仕入れ）に応じてティア1の優先案内が回ること
- 曖昧な期待を残して開始すると、後で必ずクレームになります。
  入口で正直に伝えるのが結果的に最良の顧客対応です

## 10. 業界ルール・メーカー規制 — 破ると取引停止

上流（メーカー・1次問屋）発のルールです。**違反のペナルティは自社と
問屋の取引停止**であり、事業全体を失うリスクに直結します。

### フライング販売の抑止 — 発売日「当日着」ルール

- 通常の物流なら発売日の2日前などに店着させ、発売日朝から販売できるように
  します。しかし事前着はショップによる**フライング販売（発売日前販売）**の
  温床になり、発覚するとメーカー・問屋から**取引停止の重いペナルティ**が
  科されます
- そのため自社は**発売日当日着**で統一しています。ショップから「前日に
  届けてほしい」と言われても応じないこと。これは自社と全取引ショップを
  守るためのルールです

### 販売店調査（義務化の流れ）

- 「誰に・いつ・どの仕入商品を販売したか」を各ショップから報告してもらう
  **販売店調査**が業界的に義務化されつつあります
- アプリの「販売店調査」機能で調査を管理します。ショップへの依頼・回収も
  業務の一部です。**報告に協力しないショップは取引継続が難しくなる**旨を
  含めて案内してください
- 実店舗要件・運営歴要件（9章）もこの流れの一部です。転売ヤー・無店舗
  業者に商品が流れる構造は、業界全体で塞ぎに来ています

## 11. 請求・入金・出荷までの流れ

### 請求・入金
1. 確定済み発注から請求書を発行（自動計算・プレビューあり）
2. ショップが振込 → **ショップは「振込完了を報告」できる** → 請求一覧に
   「🔔 支払い確認中」表示 + 社内へ通知メール
3. 通帳/明細で入金確認 → 請求詳細で「入金を記録」（消込）→ 入金済み
4. 入金済みになると領収書PDFを発行可能

⚠ **消込は必ず実際の入金を確認してから**。ショップの「振込報告」は自己申告であり、
消込の代わりにはなりません。

### 出荷
確定 → 出荷準備 → 出荷済（追跡番号入力で自動通知）→ 配送中 → 完了。
**納品完了日（delivered_at）が売上計上（収益認識）の基準日**です。
発売日商品は当日着（→10章）。カートン単位配送の商品（📦マーク）は
端数出荷ができない点に注意。

## 12. ⚠ 事故ポイント集 — 実際に起きたトラブルから

すべて実際に発生した事例、または業界で定番の事故です。

### 事故1: Excel取込後の「カートン数・最低発注数」放置
入荷案内リストには**カートン数の列が無い**ため、取込した商品は
カートン数・最低発注数とも**既定の12**で登録されます。
実際は24入りの商品や、12BOX未満の少数配分の商品もあります。

- **カートン24の商品が「1CT=12BOX」のまま公開** → ショップが誤発注
- **8BOX配分なのに最低発注数12** → 誰も発注できない（公開前チェックに警告が出ます）

→ **取込のたびに、カートン数と最低発注数を商品編集で確認・修正する。**
取込結果画面の黄色い注意書きと、公開前チェックの警告を必ず読む。

### 事故2: 配分の期待値管理を怠る
配分は受注後に最終決定するため、「頼んだ数が来ると思っていた」不満が
構造的に発生します（→4章）。発注受付時に確約と取れる表現を使う、
配分結果の連絡が遅れる、減った理由を説明しない——のいずれも炎上要因。

→ 確約表現を使わない。配分確定したら速やかにステータス更新（自動通知が飛ぶ）。
大きく減らした場合はひとこと添える。

### 事故3: 発注が「リクエスト止まり」のまま締切超過
在庫の引き当てはステータス**「確定」時のみ**。リクエストのまま放置すると
在庫も動かず問屋発注も漏れます。発注一覧の「要確定」表示と締切バナーを毎日確認。

### 事故4: 招待メール・パスワード設定リンクの罠
- 設定リンクは**1時間有効**。「届いてから1時間以内に設定ボタンまで完了」と案内する
- 再送すると**古いリンクは失効**。必ず最新のメールを使ってもらう
- 法人メールのセキュリティによるリンク無効化は対策済み（開いただけでは消費されない方式）

### 事故5: 保証金請求書に消費税を載せる/税込表記する
保証金は前受金＝**非課税**。システムは自動で非課税計算・表記するが、
手動で金額をいじったり、Excelで別途請求書を作るときに混ぜないこと。

### 事故6: フライング販売につながる手配
「前日に届けて」「早めに送って」に応じない（→10章）。メーカー発覚時の
ペナルティは自社の取引停止。ショップ都合でルールを曲げた時点で全員が負けます。

### 事故7: テスト・手入力データの放置
テストで作った発注・請求は集計（売掛・KPI・ランク計算）に乗ります。
動作確認は専用のテストショップ（鈴木テスト商店）で行い、作ったデータは必ず削除。

### 事故8: なりすまし系の変更をチャットで受ける
**配送先住所・返金先口座の変更は申請制**（アプリ内申請 → 自社確認 → 承認）。
メールや電話で「配送先変えて」と言われてもその場で変えない。
会社名・登録住所・メールの変更は本人確認のうえ管理者のみが行う。

| 知りたいこと | 見る場所 |

| 誰がいつ何を変更したか | 管理画面「監査ログ」（super_admin） |

| 在庫数が合わない | 発注詳細の操作履歴 + 監査ログで増減を追跡 |

わからないことは推測で操作せず、鈴木さん・河津さんに確認してください。
**金額・在庫・顧客情報に触る操作は、迷ったら止まる**が鉄則です。
