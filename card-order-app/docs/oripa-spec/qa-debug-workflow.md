# QA / デバッグ支援ワークフロー（提案）

要件定義〜実装後までを通してQAを内製化し、デバッグ工数を圧縮するための役割定義とテンプレート。
対象: ネットオリパ（NOVA / GRIM）。stg環境はMCPブラウザで実機操作可能（探索的テスト・再現確認に活用）。

---

## 1. 3フェーズでの関与

| フェーズ | 内容 | 成果物 |
|---------|------|--------|
| **A. 要件定義時QA** | 仕様の曖昧点・抜け漏れ・異常系を洗い出し、テスト観点を仕様に組み込む | テスト観点リスト（各仕様書に内蔵済）／受け入れ基準（AC）／確認事項 |
| **B. 実装後デバッグ** | 影響範囲を特定し、チェックリストで網羅検証。stg実機で探索的テスト＋回帰確認 | 影響範囲マップ／デバッグチェックリスト／不具合レポート（再現手順付き） |
| **C. 継続** | 不具合の再現・切り分け・原因仮説・修正提案、E2Eテストの作成 | 再現手順／原因仮説／パッチ案／E2Eテスト |

---

## 2. できること / できないこと（正直版）

### ✅ できる
- **要件段階のQA**: 異常系・境界値・競合・権限・冪等性などの観点出し（既に各仕様の「テスト観点」で実施）。
- **影響範囲（リグレッション）分析**: 仕様＋（コード/PR共有時は）コードから、変更が波及する画面・API・データ・既存機能を特定。
- **stg実機の探索的テスト**: MCPブラウザでログイン→画面遷移→操作→状態/ネットワーク/コンソール確認（今回の画面スキャンと同じ手法）。不具合の**再現と切り分け**。
- **PR/差分レビュー**: コードを読んでバグ・退行・抜けを指摘（`/code-review` 等）。
- **E2Eテスト作成**: Playwright等のシナリオを書き起こし。
- **不具合レポート**: 再現手順・期待/実際・影響範囲・原因仮説・修正案をセットで。

### ⚠️ 前提・限界
- コードレベルの影響範囲・修正は **リポジトリ/PRへのアクセスが必要**（フロント=stg-novagacha-frontend等）。現状この作業場(card-order-app)には実基盤コードは無い。
- 本番データ・課金・破壊的操作（削除/送金/権限変更）は実行しない（テスト環境・ダミーで実施）。
- 「バグゼロ保証」はしない。あくまで**網羅率を上げ見逃しを減らす**支援。
- 自動テスト実行は、CI/テスト基盤があれば連携可（無ければ手動＋E2E作成で補う）。

## 3. 影響範囲（インパクト）分析の型

1機能を変更したとき、次の軸で波及を洗い出す:

| 軸 | 確認内容 |
|----|----------|
| **画面** | 直接変更した画面＋同じコンポーネントを使う他画面 |
| **API/データ** | 変更したエンドポイント・テーブル・残高/在庫など共有状態 |
| **共有リソース** | コイン/BT/ポイント残高、在庫、ランキング、通知 等の整合 |
| **権限/状態** | ログイン状態・会員ランク・イベント期間内外・端末/OS |
| **既存機能の退行** | 変更箇所が壊しうる既存フロー（抽選・発送・交換・課金） |
| **同時実行** | 複数ユーザー/連打/二重送信での競合（在庫・HP・ポイント） |

## 4. デバッグチェックリスト テンプレート（実装後に使用）

```
■ 機能: <機能ID/名称>　PR: <link>　検証環境: stg
□ 正常系（ハッピーパス）
  □ 主要フローが仕様通り完了する
□ 境界値・異常系
  □ 残高/在庫=0、上限、最小、超過
  □ 不正入力・空・最大長
  □ 期間外・権限なし・未ログイン
□ 影響範囲（§3で特定した項目を列挙して確認）
  □ <画面A> 退行なし
  □ <API/残高> 整合
□ 同時実行・冪等
  □ 連打/二重送信で多重発生しない
□ UI/表示
  □ 文言・通貨単位・桁・ローディング・エラー表示
  □ レスポンシブ（SP実機幅）
□ 回帰（既存重要フロー）
  □ 抽選→演出→結果→発送/交換
  □ 課金/残高反映
□ ログ/監視
  □ エラーログ・コンソールエラーなし
判定: Pass / Fail（Failは不具合レポートへ）
```

## 5. 実例：01-f 裏ボタン の影響範囲＆デバッグチェック

### 影響範囲マップ
| 軸 | 該当 |
|----|------|
| 画面 | 演出画面（追加）、ガチャ編集（管理・設定追加）、マイページ（演出モード設定追加） |
| API/データ | ガチャ設定（裏ボタン項目）、抽選結果API（アーム情報の同梱）、ユーザー設定（演出モード） |
| 共有リソース | なし（残高は変えない）。ただし**抽選結果の機密性**（当落先バレ）に影響 |
| 権限/状態 | マナーモード（音）、演出モードOFF、賞ランク閾値、イベント無関係 |
| 既存退行 | **通常演出・スキップ**が壊れないこと（最重要）、10連/100連演出 |
| 同時実行 | タップ連打で確定音が多重再生されない |

### デバッグチェックリスト（抜粋）
```
□ OFFガチャ：タップエリア/確定音/ランプが一切出ない
□ ハズレ：何回タップしても確定音が鳴らない（誤示唆ゼロ）
□ 閾値未満当選（例:B賞でA以上設定）：鳴らない
□ 閾値以上当選：出現確率に概ね沿ってアームされる（試行で確認）
□ アーム時：タップ毎1/Nで発火、1度鳴ったら多重発火しない
□ 発火と同時にGOGOランプ点灯（消音/マナーモードでも視認）
□ マイページ演出モードOFF→裏ボタン演出が無効
□ 既存：スキップ動作・通常演出・10連/100連が退行なし
□ セキュリティ：当落/アームがクライアントだけで判定されない（改ざんで先バレしない）＝ネットワーク応答を確認
□ コンソールエラーなし／演出後に結果画面へ正しく遷移
```

## 6. 依頼の仕方（運用イメージ）

- **要件段階**: 「この仕様のテスト観点と確認事項出して」→ 観点＋AC＋曖昧点を返す。
- **実装後**: PR/差分（or stgのデプロイ）を共有 →「影響範囲とデバッグチェックリスト作って、stgで通せる範囲は検証して」→ チェックリスト＋実機検証結果（Pass/Fail＋再現手順）を返す。
- **不具合時**: 事象を共有 →「再現と切り分けして原因仮説と修正案出して」。

> まずは **フロントのリポジトリ（or PR）へのアクセス**があると、コードレベルの影響範囲・退行検出まで踏み込めます。stgのURLだけでも探索的テストは可能です。

---

## 7. まとめ
- 要件定義に**QA観点を最初から織り込む**ことで、後工程のデバッグ往復を削減。
- 実装後は**影響範囲を機械的に洗い出し→チェックリストで網羅検証→stg実機で再現確認**。
- 本書のテンプレートを各機能（01-a〜01-f / 02-a・02-b）に適用していけます。
